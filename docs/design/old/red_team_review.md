## Critical（致命的）

### C-1: AgentCore がアーキテクチャに残存 — 調査結果と設計書が矛盾

**説明**: research_findings.md は「**MVP では Step Functions + Bedrock API 直接呼び出しを推奨**」と明確に結論しているにもかかわらず、architecture_draft_v1.md のコンポーネント図（§2.1）、データフロー（§2.2）、AI パイプライン（§7.3）では依然として **AgentCore をメインのオーケストレーション基盤** として記載している。§7.3 の「AgentCore vs Step Functions の使い分け」テーブルでも AI ラベリングに AgentCore を採用としている。

**影響範囲**: §2.1 コンポーネント図、§2.2 データフロー、§7.3 全体、§10 コスト見積もり

**リスク**: 設計書をそのまま実装に進むと AgentCore の学習コスト・統合コストで **Week 2-3 がブロック** される可能性が高い。AgentCore は GA からわずか 4 ヶ月でドキュメントも事例も限られる。

**推奨**: 設計書 v2 で AgentCore を完全に除外し、AI ラベリングパイプラインを `Step Functions → Lambda(Nova Pro) → Lambda(照合) → Lambda(Guardrails + 保存)` に置き換える。AgentCore は「将来拡張候補」として付録に移動。

---

### C-2: 週次チェックイン機能がデータモデル・API に完全欠落

**説明**: idea.md と idea_japanese.md の Phase 2 に明記されている「**任意の週1チェックイン（生活イベント、親の不安スコア）**」が、アーキテクチャの以下すべてに記載されていない:

- §5.2 テーブル設計: チェックインデータを格納するテーブルが存在しない
- §4.2 API エンドポイント: チェックインの作成・取得エンドポイントなし
- §3.2 ページ構成: チェックイン入力 UI なし
- §8.2 統計アプローチ: チェックインデータのレポートへの統合方法なし

**影響範囲**: データモデル、API、UI、レポート生成

**リスク**: 原案の明示的な機能が未設計のまま実装に入ると、後から追加する際にデータモデルの変更が必要になり、既存機能にも影響が波及する。

**推奨**: `WeeklyCheckIns` テーブル（PK: `checkInId`, childId, weekStart, lifeEvents: String, caregiverAnxietyScore: Number 1-5, notes: String）を追加し、対応する API・UI・レポート統合も設計する。もしくは、MVP ではスコープ外と明示的に判断し、その旨を設計書に記載する。

---

### C-3: AI ラベル編集のフィードバック蓄積がデータモデルに未反映

**説明**: idea.md に「**Save edits as feedback**」、idea_japanese.md に「**⑤学習用フィードバック蓄積**」と記載されている。しかし:

- §5.2 Episodes テーブルの `confirmedLabel` は確定ラベルのみ格納し、「元の AI 提案との差分」を構造的に保存する設計になっていない
- AILabels テーブルと Episodes テーブルの `confirmedLabel` を突合すれば差分は推定可能だが、**何を編集したか（type の変更? severity の変更? 新規チックへの変更?）** が明示的にトラッキングされない
- フィードバックを将来の AI 改善にどう活用するかのデータパイプラインが未設計

**影響範囲**: §5.2 データモデル、§7.1-7.2 AI パイプライン

**リスク**: 原案が強調するフィードバックループの実現可能性が低下。コンペ審査でも「学習するシステム」のアピールが弱くなる。

**推奨**: Episodes テーブルに `feedbackType` (`confirmed_as_is` / `edited_type` / `edited_severity` / `edited_context` / `rejected` 等) と `originalAILabel` (Map) フィールドを追加し、差分を構造的に記録する。フィードバック集計用の GSI も検討する。

## Major（重要）

### M-1: Amazon Transcribe が設計書から完全欠落

**説明**: idea.md と idea_japanese.md の両方で AWS AI サービスとして「**Amazon Transcribe（音声の文字起こし）**」が明記されているが、architecture_draft_v1.md には一切記載がない:

- §2.1 コンポーネント図に Transcribe なし
- §7 AI/ML パイプラインに音声処理フローなし
- §10 コスト見積もりに Transcribe なし
- §7.1 のプロンプト構造にも音声テキストの入力スロットなし

**影響範囲**: §2.1, §7.1, §7.3, §10

**リスク**: vocal tic（音声チック）の分析精度に影響。咳払い・発声などの音声チックは動画フレームだけでは検出しづらく、音声の文字起こしが重要な補助情報になる。コンペで「AWS AI サービスの活用度」の評価が下がるリスクもある。

**推奨**: AI ラベリングパイプラインに Transcribe を組み込む。具体的には `動画 → (並列) Nova Pro 動画分析 + Transcribe 音声文字起こし → 統合 → 照合 → ラベル提案`。Step Functions の並列ステップで実装可能。Free Tier 枠は月 60 分あり、10-20 秒動画 100 本 = 最大 33 分で収まる。

---

### M-2: 動画の共有フロー設計が欠落 — 「レポートに代表クリップ添付」の実現方法が不明

**説明**: idea.md に「**1-3 representative clips**」を週次レポートに添付すると記載。architecture_draft_v1.md §8.2 には「代表エピソード」として `representativeEpisodeIds` が WeeklyReports テーブルにあるが:

- PDF に動画を埋め込む方法が未設計（PDF に動画は直接埋め込めない）
- Presigned URL をレポートに含める場合の有効期限問題（60 分で切れる）
- 医療者にレポートを共有する際の動画アクセス方法が未設計
- idea.md に「**Video sharing optional, with the summary as default**」とあるが、オプトイン/オプトアウトの UI・API 設計がない

**影響範囲**: §8 レポート生成、§6 メディアパイプライン、§4.2 API（共有エンドポイント）

**リスク**: 「代表クリップ付きレポート」はプロダクトの差別化ポイント。共有フローが未設計のままだと、Week 4 でレポート機能を実装する際に混乱が生じる。

**推奨**:
1. PDF にはサムネイル + QR コード（長期有効な共有リンクへ）を埋め込む
2. 共有リンク用の `ShareTokens` テーブルを追加（有効期限付き一時トークン）
3. `/children/{childId}/reports/{reportId}/share` エンドポイントで共有リンク生成
4. 動画共有のオプトイン設定を UI に追加

---

### M-3: データ削除フローが具体性に欠ける — 子どもの健康データに対する不十分な設計

**説明**: §9.3 に「アカウント削除時にすべてのデータを削除」とあるが:

- 削除の具体的なフローが未設計（どのテーブルをどの順序で削除するか）
- S3 の動画・レポートの削除方法が未記載（オブジェクト削除? バケットライフサイクル?）
- S3 Glacier に移行された動画（§6.4: 90 日後に Glacier 移行）の削除手順が未考慮
- **個別エピソードの削除** が API にはあるが、関連する VideoMetadata、AILabels、S3 オブジェクトのカスケード削除ロジックが未設計
- 「ユーザー制御のデータ保持期間」の設定がどのように自動削除を実行するかが不明

**影響範囲**: §9.3 プライバシー、§4.2 API（DELETE エンドポイント）、§6 メディアパイプライン

**リスク**: 子どもの健康データを扱うアプリで「データ削除が不完全」は重大なリスク。COPPA（米国）や GDPR の文脈でも問題になり得る。プロトタイプとはいえ、コンペ審査でプライバシー設計の不備を指摘される可能性がある。

**推奨**:
1. カスケード削除のシーケンスを設計（DynamoDB 全関連レコード + S3 オブジェクト + Glacier オブジェクト）
2. Step Functions による非同期削除ワークフローを設計
3. 保持期間ベースの自動削除には EventBridge Scheduler + Lambda を活用
4. 削除完了を確認するチェックポイントを設ける

---

### M-4: 一括レビュー（バルクエディット）機能の API・UI が未設計

**説明**: idea.md に「**Parents confirm or bulk-edit later**」、idea_japanese.md に「**後からまとめて確認・修正できます**」と記載。しかし:

- §4.2 のエピソード API は個別の GET/PUT のみで、一括操作のエンドポイントがない
- §3.2 のページ構成に「未確認ラベル一括レビュー」画面がない
- §5.2 に `childId-labelStatus-index` GSI はあるが、一括更新 API がない

**影響範囲**: §4.2 API、§3.2 UI ページ構成

**リスク**: 親の利便性に直結する機能。個別にエピソードを開いてラベルを確認する UX は、忙しい親にとって大きな摩擦となる。

**推奨**:
1. `PUT /children/{childId}/episodes/bulk-confirm` エンドポイントを追加（複数 episodeId の labelStatus を一括で `confirmed` に更新）
2. `/review` ページを追加（未確認ラベルのリスト表示 + スワイプ操作 or チェックボックスによる一括確認）

---

### M-5: オフライン対応の設計が不足 — PWA の本質的価値が未活用

**説明**: §3.1 で PWA / Serwist を採用と記載しているが、オフライン時の動作設計が不足:

- 外出先・移動中でチックを目撃してもネットワーク接続がない場合がある
- 動画撮影は可能だが、S3 へのアップロードにはネットワークが必要
- チックカードのワンタップ記録もオフライン時にどうなるか未設計
- Service Worker でのキャッシュ戦略（キャッシュファースト vs ネットワークファースト）が未定義

**影響範囲**: §3.1 PWA、§3.3 動画キャプチャ UX フロー、§6.2 アップロードフロー

**リスク**: 親がチックを目撃する瞬間は予測不可能。ネットワークなしで記録できないと、アプリの最大の価値が失われる場面が多発する。

**推奨**:
1. IndexedDB にエピソード・動画を一時保存するオフラインキュー設計
2. ネットワーク復帰時のバックグラウンド同期（Background Sync API）
3. チックカード記録は完全オフライン対応（ローカルに保存→同期）
4. ただし、29 日間の制約を考慮し、MVP では「ネットワーク必須、オフライン対応は Phase 2」と明示的にスコープを定義するのも一つの判断

---

### M-6: Step Functions の週次レポート生成で全ユーザー分の並列実行設計が欠落

**説明**: §8.1 のレポート生成ワークフローで「子ども一覧取得 → 各子どものエピソード集計」とあるが:

- **全ユーザーの全子どもに対して** 毎週月曜 9:00 JST に一斉実行する場合の並列化設計がない
- Step Functions の Map ステート（並列イテレーション）の使用が未記載
- Lambda の同時実行数制限（Free Tier: 同時実行 10）との兼ね合いが未考慮
- Bedrock Claude の呼び出しがボトルネックになる可能性（レート制限）

**影響範囲**: §8.1 オーケストレーション

**リスク**: プロトタイプ段階ではユーザー数が少ないため顕在化しにくいが、設計の完成度としてコンペ審査で指摘される可能性がある。

**推奨**: Step Functions の Distributed Map または Inline Map ステートを使用し、子ども単位で並列実行。Lambda 同時実行数と Bedrock レート制限を考慮した concurrency 設定を明記。プロトタイプ向けには `MaxConcurrency: 3` 程度で十分。

## Minor（軽微）

### m-1: DynamoDB の `childId-labelStatus-index` GSI の設計が不適切

**説明**: §5.2 Episodes テーブルの GSI `childId-labelStatus-index`（PK: `childId`, SK: `labelStatus`）は、`labelStatus` が低カーディナリティ（4 値: `pending`, `ai_suggested`, `confirmed`, `edited`）であり、ソートキーとしての効率が悪い。同一 `labelStatus` 内でのソートができない。

**推奨**: GSI を `childId-labelStatus-occurredAt-index`（PK: `childId#labelStatus` 複合キー, SK: `occurredAt`）に変更するか、フィルタ式を使う設計に変更。もしくはシンプルに `childId-occurredAt-index` で取得して、アプリ側で `labelStatus` をフィルタする方が実用的（プロトタイプ規模のデータ量なら問題なし）。

---

### m-2: S3 バケットが 1 つに統合されているが、メディアとナレッジの IAM ポリシーが混在するリスク

**説明**: §6.1 で `tictrack-media-{env}/` の下に `videos/`, `reports/`, `knowledge/` を配置しているが、`knowledge/` は Knowledge Bases 用でシステムデータ、`videos/` はユーザーの個人データ。同一バケット内でプレフィックスベースのポリシー分離は可能だが、IAM ポリシーの複雑性が増す。

**推奨**: プロトタイプではこのまま進めて問題ないが、コンペ説明資料では「本番ではバケット分離を推奨」と注記する。

---

### m-3: EventBridge Scheduler のトリガー時刻「毎週月曜 9:00 JST」がハードコード前提

**説明**: §8.1 でトリガー時刻が固定だが、ユーザーのタイムゾーンや好みに応じた設定変更ができない。

**推奨**: プロトタイプでは固定で問題ないが、ユーザー設定テーブルにタイムゾーン・レポート配信曜日を持たせておくと拡張しやすい（実装は後回しで可）。

---

### m-4: Presigned URL の有効期限が用途で統一されていない

**説明**: §9.2 で「アップロード: 5 分、閲覧: 60 分」とあるが、§6.2 のアップロードフロー説明でも「5 分有効」と記載。レポート PDF の閲覧 URL や、代表クリップの閲覧 URL の有効期限は未定義。特に医療者に共有するレポートの URL が 60 分で切れると実用に耐えない。

**推奨**: 用途別に整理:
- アップロード: 5 分（現状通り）
- アプリ内閲覧: 60 分（現状通り）
- 共有用: 24-72 時間、または共有トークンベースの独立エンドポイント

---

### m-5: UI ライブラリ選定で shadcn/ui は Tailwind CSS v4 との互換性に注意

**説明**: §3.1 で Tailwind CSS + shadcn/ui を選定しているが、2025 年に Tailwind CSS v4 がリリースされており、shadcn/ui の Tailwind v4 対応状況を確認する必要がある。

**推奨**: 実装開始時に shadcn/ui の最新版と Tailwind v4 の互換性を確認。問題がある場合は Tailwind v3 で固定するか、Radix UI Primitives を直接使用する。

---

### m-6: `VideoMetadata` テーブルの PK が `episodeId` で Episode と 1:1 だが、別テーブルにする必要性が薄い

**説明**: §5.2 の VideoMetadata テーブルは Episodes テーブルと 1:1 対応（PK: `episodeId`）。Episodes テーブルの属性としてフラットに持たせた方がシンプル。マルチテーブル設計を採用しているとはいえ、1:1 のエンティティを別テーブルに分けるのはオーバーヘッド。

**推奨**: Episodes テーブルに `videoS3Key`, `videoMimeType`, `videoFileSize`, `uploadStatus`, `thumbnailS3Key` を直接追加し、VideoMetadata テーブルを廃止。`recordType === 'video'` の場合のみこれらの属性が存在する設計で十分。

---

### m-7: コスト見積もりが research_findings.md の結論と不整合

**説明**: §10 のコスト見積もりは Bedrock 合計 $10-15/月と記載しているが、research_findings.md は「**$3-6/月に下方修正すべき**」と結論。Nova Pro の見積もりが $5-8 のまま更新されていない。

**推奨**: research_findings.md の調査結果に基づき、§10 のコスト見積もりを更新（Nova Pro: ~$0.40、Claude Haiku: ~$1-2、その他: ~$1-2、合計: ~$3-6/月）。

## Observation（所見）

### O-1: Bedrock Guardrails の効果検証計画がない

§7.4 で Guardrails の設定方針は定義されているが、「non-diagnostic が本当に担保されるか」の体系的なテスト計画がない。プロンプトインジェクションや巧妙な質問パターンに対する Guardrails の堅牢性を、早期に Red Team テスト（悪意あるプロンプトのテスト集）で検証すべき。§11.4 に「Guardrails テスト: カスタムテストスイート」とあるが、具体的なテストケースの定義が必要。

---

### O-2: 「non-diagnostic」の法的・倫理的な境界線が未定義

idea.md で「non-diagnostic: no diagnosis or treatment advice」と記載しているが、以下が未定義:
- severity 1-3 のラベル提案は「診断的行為」に該当しないか？
- 「週ごとに悪化傾向」というレポート表現は「予後予測」に近くないか？
- 免責事項の文言は法的に十分か？

プロトタイプとはいえ、子どもの健康データを扱うため、コンペ審査員に質問された場合の回答を準備しておくべき。

---

### O-3: 認証フローで「家族共有」機能が Cognito の標準機能だけでは不十分

idea.md に「Amazon Cognito for auth and family sharing」とあるが、Cognito は個人認証サービスであり、「家族内で同じ子どものデータを複数ユーザーが閲覧・編集する」ための共有機能は標準で備わっていない。§4.2 API にもデータ共有のエンドポイントがない。

MVP ではシングルユーザー前提で問題ないが、「家族共有」を謳う場合はアプリケーションレベルの共有ロジック（招待・権限管理）が別途必要。

---

### O-4: 29 日間のスプリント計画が楽観的

§付録のスプリント計画:
- Week 1: 基盤構築（Amplify + Cognito + DynamoDB + API Gateway）
- Week 2: Phase 1 MVP（動画キャプチャ、チックカード、CRUD）
- Week 3: AI パイプライン（Bedrock 統合、ラベリング）
- Week 4: レポート + マイクロガイド + Builder Center 記事

懸念点:
- Week 1 で Amplify Gen 2 + Next.js の初期設定に想定以上の時間を要するリスク（特に Cognito 統合のデバッグ）
- Week 3 の Bedrock 統合で Nova Pro のプロンプトエンジニアリングに試行錯誤が必要
- Week 4 に **レポート生成 + マイクロガイド(RAG) + Builder Center 記事** の 3 つを詰め込みすぎ
- research_findings.md が推奨する「Week 1 での Nova Pro PoC」がスプリント計画に反映されていない
- TDD でのテスト作成時間が計画に含まれていない

---

### O-5: マイクロガイドのナレッジソースのキュレーション工数が未見積もり

§7.5 に「信頼できる医療機関・公的機関の資料（キュレーション済み）」とあるが、このキュレーション自体に相当な工数がかかる:
- 信頼できるソースの選定・収集
- マークダウンへの変換・構造化
- 内容の正確性検証
- Knowledge Bases へのインジェスト・テスト

29 日間の開発期間内にこれを完了するのは厳しい。最小限のナレッジ（3-5 記事程度）でデモ可能なレベルに絞るべき。

---

### O-6: COPPA / 児童オンラインプライバシー保護に関する考慮が皆無

本アプリは子どもに関する健康データ（動画含む）を収集・保存する。米国向けの場合、**COPPA（Children's Online Privacy Protection Act）** の適用可能性を検討すべき:
- 13 歳未満の子どもの個人情報を収集する場合、保護者の同意が必要
- TicTrack は「保護者が入力」するため直接 COPPA 違反にはなりにくいが、子どもの動画は「子どもの個人情報」に該当する可能性が高い
- コンペ審査で「児童データ保護への考慮」を問われた場合の回答を準備すべき

プロトタイプとして最低限必要な対応:
- プライバシーポリシーに COPPA への言及を含める
- 保護者の明示的同意フローを設計（サインアップ時）
- データ最小化の原則を徹底

### O-7: Nova Pro の 672×672 リサイズによる細かい運動チック検出への影響

research_findings.md で指摘されている通り、Nova Pro は入力画像を 672×672 にリサイズする。瞬き・眉の動きなどの微細な運動チックは、このリサイズで情報が失われる可能性がある。research_findings.md は「フォールバック戦略: 親が分類」を推奨しているが、この制限をユーザーにどう伝えるか（「AI は大きな動きの検出に優れています。細かい動きは手動ラベルをお勧めします」等）の UX 設計が必要。

### O-8: 設計書に Amplify Gen 2 のバックエンド定義方法の記載がない

research_findings.md では「バックエンド定義は `amplify/backend.ts` で TypeScript コードファースト」と記載。しかし architecture_draft_v1.md では Amplify Gen 2 のバックエンド構成（`amplify/` ディレクトリの構造、リソース定義方法、カスタム Lambda の統合方法）が一切記載されていない。Amplify Gen 2 の `defineBackend`, `defineAuth`, `defineData` などの API 設計がアーキテクチャに影響するため、設計書に含めるべき。
