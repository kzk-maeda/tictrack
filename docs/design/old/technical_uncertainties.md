## P1: ブロッキング（実装開始前に解決必須）

### P1-1: Bedrock の料金モデルとコンペ予算

**疑問**: Bedrock は AWS Free Tier 対象外であり、プロトタイプ使用で月額 ~$12-15 のコストが発生する見込み。コンペのルール「AWS Free Tier 内」という制約との整合性はどうなるか?

**重要な理由**:
- コンペ要件には「Stay within AWS Free Tier limits」とある
- 一方でコンペは「AWS AI services」の活用を明示的に推奨しており、Bedrock を主要 AI サービスとしてリストしている
- Bedrock なしではアプリの核心機能（AI ラベリング、Guardrails、RAG）が成立しない

**想定されるアプローチ**:
1. **コンペ FAQ/ルールの精査**: Bedrock が Free Tier 例外として認められているか確認
2. **コンペ主催者への質問**: 不明な場合、Builder Center コミュニティや公式チャネルで確認
3. **コスト最小化戦略**: 仮に自己負担なら、Haiku モデル使用、リクエスト数制限、キャッシュ活用で $10/月以下に抑制
4. **代替案**: Bedrock 以外の Free Tier AI サービス（SageMaker Serverless の Free Tier 枠等）の検討（ただし Guardrails/AgentCore は Bedrock のみ）

**調査アクション**:
- [ ] コンペ公式ルール（Terms and Conditions）を精読
- [ ] Builder Center コミュニティで他参加者の質問/回答を検索
- [ ] 必要に応じてコンペ主催者に直接質問

### P1-2: Amazon Nova Pro の動画分析精度（チック検出）

**疑問**: Nova Pro は 10〜20 秒の動画から運動チック（首振り、瞬き等）や音声チック（咳払い、声等）を確実に検出・分類できるか?

**重要な理由**:
- AI ラベリングはアプリのコア価値提案
- チックの動きは微妙で短時間のことが多く、一般的な動画理解とは異なる難易度
- 精度が低い場合、親にとって「使えない」提案になり UX が悪化する
- プロトタイプとして説得力のあるデモが必要

**想定されるアプローチ**:
1. **早期 PoC 実施**: 5〜10 本のサンプル動画（公開データセット or 自作シミュレーション）で Nova Pro の出力を検証
2. **プロンプト最適化**: 詳細な指示（チックの典型的パターン記述、期待する出力形式）でプロンプトを調整
3. **フォールバック戦略**:
   - Nova Pro の精度が不十分な場合 → Claude のマルチモーダル機能（動画対応次第）
   - 動画のキーフレーム抽出 → 静止画ベース分析にフォールバック
   - 最悪の場合: AI は「疑わしい動きの検出」のみ行い、分類は親に委ねる
4. **ハイブリッドアプローチ**: Nova Pro で大まかな検出 → Claude で詳細分類、という 2 段階パイプライン

**調査アクション**:
- [ ] Nova Pro の動画入力 API の仕様確認（最大動画長、サポート形式、フレーム数制限）
- [ ] チック症状のサンプル動画の準備（プライバシーに配慮）
- [ ] PoC スクリプト作成・実行（3〜5 日以内）
- [ ] プロンプトエンジニアリングのイテレーション

### P1-3: AgentCore vs Step Functions のオーケストレーション戦略

> **ステータス**: ✅ **決定済み**（2026-03-06）
> **決定**: **Strands Agents SDK + AgentCore Runtime を採用**
> **決定理由**: AWS の最新 AI Agent 技術を学習・活用（コンペの目的に合致）。Agent のツール呼び出しパターンにより、Step Functions + 複数 Lambda より実装がシンプル化。フォールバックも容易（Lambda Python への移行が最小限の変更で可能）。
> **詳細**: `research_findings.md` §3b を参照

**疑問**: AI ラベリングパイプラインは AgentCore で実装すべきか、Step Functions で実装すべきか? 両者の使い分けの最適な境界は?

**重要な理由**:
- オーケストレーション方式の選択は全体アーキテクチャに大きく影響
- AgentCore はまだ比較的新しいサービスで、実装パターンの情報が限定的
- 29 日の期間で未知のサービスへの学習コストを最小化したい
- コンペ審査で「AWS AI サービスの効果的活用」が評価される

**最終決定（ハイブリッド — Agent + Step Functions）**:
- **Strands Agent (AgentCore)**: AI ラベリングパイプライン（Tic Labeling Agent）、マイクロガイド（Micro-Guide Agent）
- **Step Functions（維持）**: 週次レポート生成（定型ワークフロー）、データ削除カスケード
- レポートテキスト生成ステップでは `strands.Agent` をインライン使用

**調査アクション**:
- [x] AgentCore の最新ドキュメント・サンプルコードを確認
- [x] AgentCore の料金体系を確認（$200 Free Tier クレジットあり）
- [x] Strands Agents SDK の調査（OSS、Python、@tool デコレータ）
- [x] Step Functions との統合パターンを調査（レポート生成は Step Functions 維持）

## P2: 重要（早期に解決すべき）

### P2-1: モバイル Web 動画キャプチャ UX

**疑問**: PWA（モバイルブラウザ）から MediaRecorder API を使った動画撮影は、十分な UX 品質を提供できるか?

**重要な理由**:
- 動画キャプチャはユーザーの最初のインタラクション。UX が悪いと即離脱
- ブラウザ間（特に Safari/iOS）の MediaRecorder API 互換性に課題がある
- PWA からのカメラアクセスは OS やブラウザの権限管理に依存
- ネイティブアプリと比較した制限（バックグラウンド録画不可等）

**想定されるアプローチ**:
1. **MediaRecorder API + getUserMedia**:
   - 対応状況: Chrome/Android は良好、Safari/iOS は 14.5+ で対応（制限あり）
   - `video/webm` (Chrome) vs `video/mp4` (Safari) の形式差異への対応
2. **代替案: `<input type="file" capture="environment">`**:
   - ネイティブカメラアプリを起動する方式
   - ブラウザ互換性は高いが、リアルタイム UI 制御ができない（カウントダウン表示等不可）
3. **ハイブリッドアプローチ**:
   - 対応ブラウザでは MediaRecorder API を使用
   - フォールバックとして `<input capture>` を提供

**調査アクション**:
- [ ] iOS Safari での MediaRecorder API の最新対応状況を確認（iOS 17+ のサポート状況）
- [ ] サンプルアプリで実機テスト（iPhone, Android）
- [ ] 動画フォーマットの変換要否を確認（WebM → MP4 の変換が必要か?）
- [ ] PWA カメラ権限のフロー確認（HTTPS 必須等）

### P2-2: Missing-Data Tolerant な統計手法

**疑問**: 不完全な観察データから、医療者にとって有意義かつ誤解を招かない統計情報をどう生成するか?

**重要な理由**:
- 「欠測に強い」はアプリの核心的な差別化ポイント
- 統計が不正確・誤解を招く場合、医療現場で問題になる可能性
- 過剰な統計は親の不安を煽る可能性がある
- 記録日数が少ない週のレポートをどう扱うか

**想定されるアプローチ**:

1. **記述統計に限定（推奨）**:
   - 「記録された範囲では〜」という前提を明示
   - 記録カバレッジの表示（5/7 日記録等）
   - 全件カウントは表示しない（「少なくとも X 回」という表現）

2. **正規化手法**:
   - 記録日数ベースの正規化: 「1 記録日あたりの平均エピソード数」
   - 記録時間帯の考慮: 記録がない時間帯はグレーアウト表示

3. **変化点検出**:
   - 前週比は同一条件（記録日数で正規化した値）で比較
   - 有意な変化のみハイライト（微小な変動はノイズとして扱う）

4. **最低記録数閾値**:
   - 週に 3 日未満の記録: 「記録が少ないため、傾向分析は省略します」と表示
   - 1 件もない週: 空レポート or 「今週の記録はありません」

**調査アクション**:
- [ ] 欠測データの扱いに関する既存研究/ベストプラクティスの調査
- [ ] 医療向け症状追跡アプリでの統計表示の事例調査
- [ ] 統計表示のモックアップ作成（親・医療者双方の視点で検証）

### P2-3: Lambda での PDF 生成

**疑問**: Lambda（Node.js 20 ランタイム）で、グラフやチャートを含む見栄えの良い PDF をどう生成するか?

**重要な理由**:
- 週次レポート PDF はアプリの重要な成果物（医療者に共有される）
- Lambda には 512MB の /tmp 制限、15 分のタイムアウト制限がある
- ブラウザベースの PDF 生成（Puppeteer 等）は Lambda レイヤーが重い

**想定されるアプローチ**:

| ライブラリ | 特徴 | Lambda 適性 |
|-----------|------|-------------|
| **pdfkit** | プログラマティック PDF 生成、軽量 | ◎（ネイティブ依存なし） |
| **@react-pdf/renderer** | React コンポーネントで PDF レイアウト | ○（Node.js で使用可能） |
| **Puppeteer (chrome-aws-lambda)** | HTML → PDF、見栄え最高 | △（レイヤー重い ~50MB、起動遅い） |
| **pdfmake** | 宣言的な PDF 定義 | ◎（軽量、テーブル/チャート対応） |

**推奨**: `pdfkit` または `pdfmake`
- Lambda デプロイパッケージが小さい
- チャートは `chart.js` の Canvas レンダリング → 画像として埋め込み
- または、統計データをテキスト/テーブル形式で表示（グラフは簡易的に）

**調査アクション**:
- [ ] pdfkit + chart.js のサンプル PDF 生成 PoC
- [ ] Lambda レイヤーのサイズと起動時間を計測
- [ ] レポートのデザインモック作成

### P2-4: Amplify Gen 2 + Next.js PWA の構成

**疑問**: Amplify Gen 2 で Next.js PWA をデプロイする際の具体的な設定方法と制約は?

**重要な理由**:
- フロントエンドのデプロイ基盤選択はプロジェクト初期に確定すべき
- Amplify Gen 2 は CDK ベースで Gen 1 と大きく異なる
- PWA の Service Worker 設定と Amplify のビルド設定の統合に注意が必要

**想定されるアプローチ**:
1. **Amplify Gen 2 + next-pwa**:
   - `amplify/backend.ts` でバックエンドリソース定義（Auth, API, Storage）
   - `next.config.js` で `next-pwa` プラグイン設定
   - Amplify ビルド設定で Service Worker の生成を確認

2. **Amplify Gen 2 + Serwist (next-pwa の後継)**:
   - next-pwa はメンテナンスが停滞気味
   - Serwist が推奨される代替

3. **注意点**:
   - Amplify の SSR サポートと PWA オフライン対応の両立
   - Amplify の環境変数管理（Bedrock API キー等は Lambda 側で使用）

**調査アクション**:
- [ ] Amplify Gen 2 + Next.js の公式チュートリアル実施
- [ ] PWA プラグイン (next-pwa or Serwist) の Amplify 上での動作確認
- [ ] Amplify Gen 2 のビルド設定テンプレート確認

### P3-3: DynamoDB シングルテーブル vs マルチテーブル

**疑問**: 本プロジェクトに最適な DynamoDB テーブル設計は?

**重要な理由**:
- テーブル設計はデータアクセスのパフォーマンスとコストに影響
- プロトタイプ段階での最適解は本番と異なる可能性

**想定されるアプローチ**:

| 方式 | メリット | デメリット |
|------|---------|-----------|
| シングルテーブル | クエリ効率、トランザクション | 設計の複雑さ、可読性 |
| マルチテーブル | シンプル、可読性高い | GSI 増加、クロステーブルクエリ |

**推奨**: マルチテーブル（プロトタイプ段階）
- 開発速度を優先
- エンティティ間のジョインが少ない
- 将来的な移行はコンペ後の課題

### P3-4: 動画圧縮/最適化

**疑問**: アップロード前に動画を圧縮すべきか? その方法は?

**重要な理由**:
- 動画サイズは S3 ストレージコストとアップロード時間に影響
- ただしプロトタイプでは使用量が限定的

**想定されるアプローチ**:
1. **ブラウザ側での圧縮**: MediaRecorder API の `videoBitsPerSecond` パラメータで品質調整
2. **サーバー側での圧縮**: Lambda + FFmpeg レイヤー（複雑さ増加）
3. **圧縮なし**: 10〜20 秒の動画は 720p で 2〜5 MB 程度、プロトタイプでは許容範囲

**推奨**: MediaRecorder の品質パラメータ設定のみ（プロトタイプ段階では追加の圧縮処理は不要）

**調査アクション**:
- [ ] MediaRecorder の `videoBitsPerSecond` 設定テスト
- [ ] Nova Pro が受け付ける動画形式・サイズの上限確認
