## My Vision

子どもにチックの兆候が見られたとき、保護者は「いつ起きるのか」「どのくらいの頻度なのか」を正確に把握し、医療者に伝えることに苦労します。症状は変動し、常に見守ることはできず、記録には必ず見逃しが生じます。そして何より、医療の専門知識がない保護者にとって、チック症状を言葉で正確に表現すること自体が非常に難しいのです。

TicTrack は、この課題を解決する caregiver-first / non-diagnostic なアプリケーションです。

**動画からの AI 自動ラベリング** が TicTrack の核です。保護者がスマートフォンで 10〜20 秒の短い動画を撮影すると、Amazon Bedrock の Nova Pro モデルが動画を解析し、症状名・種類（運動性/音声性）・複雑性・強度・信頼度・タイムスタンプ付き観察内容を構造化ラベルとして自動提案します。保護者が「あの動き、なんて表現すればいいんだろう」と悩む必要はもうありません。

すでに把握している症状については、**チックカード** として登録しておくことで、ワンタップで記録できます。新しい症状は動画 + AI で、既知の症状はワンタップで。この二つの記録手段を組み合わせることで、日常の中で無理なく記録を続けられます。

さらに、服薬状況や生活イベント（転校・引っ越し等）もストレスレベルとともに記録でき、**ダッシュボード** でタイプ分布・重症度分布・時間帯パターンなどの傾向を可視化します。この情報は医療機関への受診時にそのまま活用でき、「最近どうですか？」と聞かれたとき、記憶ではなくデータに基づいて説明できます。

## Why This Matters

私自身、息子のチック症状に直面し、「いつ・どのくらい起きているか」を説明することの難しさと不安を強く感じました。これは私だけの問題ではありません。

**子どもの 5 人に 1 人** が成長の過程で何らかのチック症状を経験するといわれています。決して珍しいことではないのに、保護者を支える記録ツールはほとんど存在しません。

既存のセルフトラッキングツールは、本人が自覚して記録することを前提としていますが、保護者には異なるアプローチが必要です。子どもの症状を 24 時間観察することは不可能で、見逃し（欠測）は避けられません。TicTrack は、この **missing-data tolerant**（欠測に強い）設計を前提としています。

TicTrack がもたらす価値:

- **保護者の負担軽減**: ワンタップ記録と AI 自動ラベリングで、記録の摩擦を最小化
- **症状の言語化支援**: AI が医療者にも伝わる構造化情報を生成し、「説明できない」不安を解消
- **医療者との連携改善**: データに基づく受診で、限られた診察時間を有効活用
- **文脈の記録**: 服薬や生活環境の変化と症状の関連を可視化

本アプリは **non-diagnostic**（診断・治療助言は行わない）です。AI はあくまで提案であり、最終的な確認や修正は保護者自身が行います。

### 主な機能

- **動画撮影 + AI 自動ラベリング**: Amazon Bedrock Nova Pro による動画解析と構造化ラベル提案
- **チックカード**: よく見られる症状のワンタップ記録
- **タイムライン**: カレンダー表示で記録を振り返り
- **投薬管理**: 服薬状況のワンタップ記録
- **出来事記録**: 生活イベントとストレスレベルの記録
- **ダッシュボード**: 統計的な傾向可視化と医療機関向け情報提供
- **デモモード**: サインアップ不要でアプリを体験
- **PWA**: アプリストア不要、スマートフォンのブラウザから利用可能

## How I Built This

### アーキテクチャ概要

TicTrack は Amplify Gen2 のサーバーレスアーキテクチャを基盤に、デュアル言語構成で構築しています。

<!-- TODO: アーキテクチャ図を挿入 -->
![Architecture Diagram](./architecture_diagram.png)

**データフロー:**

1. **フロントエンド**: Next.js 14 PWA（Serwist）が Amplify Hosting 上で動作
2. **認証**: Amazon Cognito で保護者の認証・認可を管理（COPPA 同意フラグ付き）
3. **API**: API Gateway + Cognito Authorizer を経由し、Lambda (api-handler) が CRUD 処理を実行
4. **データ保存**: DynamoDB に 12 テーブル（Users, Children, TicCards, Episodes, AILabels 等）、動画は S3 に保存
5. **AI 分析ワークフロー**: 動画アップロード後、Step Functions がオーケストレーションを実行。AgentCore Runtime 上の Strands Agent が Nova Pro で動画を解析し、構造化ラベルを DynamoDB に保存

### 主要な技術的決定

**1. 動画解析に Nova Pro を採用**

動画のマルチモーダル解析には Amazon Nova Pro を選択しました。S3 URI からの直接入力に対応しており、動画のダウンロードやエンコードが不要です。コストは 1 動画あたり約 $0.004 と非常に低く、プロトタイプに最適です。

**2. Step Functions によるワークフロー管理**

AI 分析は非同期処理であり、タイムアウト・リトライ・エラーハンドリングが必要です。Step Functions により、これらを宣言的に定義でき、Lambda のコードをシンプルに保てます。失敗時は自動的にエピソードのステータスを "failed" に更新します。

**3. Amplify Gen 2 + CDK カスタムコンストラクト**

Amplify Gen 2 は認証・ストレージ・ホスティングを簡単にセットアップでき、CDK カスタムコンストラクトで DynamoDB テーブル・API Gateway・Step Functions などを追加できます。一つの `backend.ts` からすべてのインフラを管理し、段階的にリソースを有効化する staged activation パターンを採用しました。

**4. Strands Agent の 5 ツール構成とマルチモーダル統合**

AI ラベリングの核となる Tic Labeling Agent は、Strands Agents SDK で構築した 5 つの専用ツールで構成されています。

1. **analyze_video** — Nova Pro が S3 上の動画を直接解析し、動作の種類・タイミング・強度を抽出
2. **transcribe_audio** — Amazon Transcribe が音声トラックから音声チック（咳払い・鼻すすりなど）を検出
3. **integrate_results** — 動画と音声の結果を統合し、2 軸分類（type × complexity）で構造化ラベルを生成
4. **apply_guardrails** — Bedrock Guardrails で診断的表現をブロック。未構成時はキーワードフィルタリングに自動降格
5. **store_label** — 結果を DynamoDB の AILabels テーブルに保存し、エピソードのステータスを更新

エージェントのオーケストレータには Claude Sonnet 4.5 を採用し、各ツールの呼び出し順序と引数を動的に判断します。動画解析（視覚）と音声解析（聴覚）を別ツールとして独立させることで、一方が失敗しても他方の結果で分析を継続できる耐障害性を実現しています。

**5. 多層的な安全設計（non-diagnostic 制約）**

ヘルスケア領域の AI として、non-diagnostic 制約を複数のレイヤーで担保しています。

- **プロンプトレイヤー**: システムプロンプトで「観察的表現のみ使用」「診断・治療助言の禁止」を指示
- **Guardrails レイヤー**: Bedrock Guardrails がトピックポリシーで診断的表現を検出・サニタイズ
- **Fallback レイヤー**: Guardrails 未構成時、禁止キーワード（「診断」「治療」「Tourette」等）のフィルタリングで代替
- **サニタイズ処理**: 違反検出時は "is diagnosed" → "appears to show"、"causes" → "is associated with" のように観察的表現に置換

AI が生成するすべてのテキストがこれらのフィルタを通過することで、保護者に不安を与える断定的な医療表現を防いでいます。

**6. 非同期分析パイプラインと段階的 Fallback**

動画分析は数十秒〜数分を要するため、完全な非同期パイプラインとして設計しています。

1. フロントエンドが `POST /episodes/{id}/analyze` を呼び出すと、Lambda (start-analysis) が即座に **202 Accepted** を返却
2. バックグラウンドで Step Functions が起動し、agentcore-proxy Lambda 経由で AgentCore Runtime 上のエージェントを呼び出し
3. 完了後、エピソードのステータスが `analyzing` → `ai_suggested` に更新され、フロントエンドがポーリングで検知

Step Functions のリトライポリシー（3 回、指数バックオフ 2.0、初期間隔 10 秒）とタイムアウト（15 分）により、一時的な障害は自動回復します。回復不能な失敗時は `MarkAsFailed` ステートがエピソードを `failed` に更新し、保護者には再試行を促す UI を表示します。


### Kiro を使った開発

TicTrack の開発では、Kiro IDE の仕様駆動開発（Spec-driven Development）ワークフローを活用しました。

**Steering Files によるプロジェクトコンテキストの確立:**
開発の初期段階で、Kiro の Steering Files にプロダクト概要・技術スタック・ディレクトリ構成を定義しました。これにより、Kiro のエージェントがプロジェクトのコンテキストを正確に理解した上でコード生成やリファクタリングを支援してくれました。

**Specs による設計の事前定義:**
各実装ステップの要件を EARS 形式で定義し、アーキテクチャ設計と実装タスクを Kiro の Specs として管理しました。これにより、コードを書く前に要件・受け入れ条件・テスト項目が明確になり、TDD アプローチとの相性が良好でした。

**AWS MCP Server によるクラウドリソースへの直接アクセス:**
[AWS Labs MCP Servers](https://github.com/awslabs/mcp) を Kiro のエージェントに接続し、DynamoDB テーブルのデータ確認、CloudWatch ログの検索、Lambda の実行状況の確認といったクラウド上のリソースへのアクセスをエージェント自身に移譲しました。これにより、AWS コンソールとエディタを行き来することなく、ログやデータの確認もエージェントとの対話の中で完結し、デバッグと開発のサイクルを大幅に高速化できました。

仕様駆動のアプローチと MCP によるクラウドリソースアクセスの組み合わせにより、10 ステップの実装ロードマップに沿って段階的に機能を追加でき、スコープクリープを防ぎながら数日の開発期間内で MVP を完成させることができました。

## What I Learned

### 1. AI の制約設計が最も重要

TicTrack は non-diagnostic アプリです。AI が何を「しない」かの設計が、何を「する」かよりも重要でした。診断や治療助言を行わない制約は、Bedrock Guardrails とプロンプト設計の両方で担保しています。ヘルスケア領域での AI 活用において、安全な制約設計の重要性を学びました。

### 2. 欠測を前提とした設計思想

一般的なトラッキングアプリは「すべてのデータが揃っている」ことを前提としますが、チック症状の記録では見逃しが必然です。「記録できた範囲から傾向を読み取る」という missing-data tolerant な設計思想は、ダッシュボードの統計表示や将来の週次レポート生成において一貫して適用しています。

### 3. Step Functions によるワークフロー管理の威力

AI 分析は外部サービス呼び出しを含む非同期処理であり、タイムアウト・リトライ・部分失敗への対処が必要です。当初は Lambda 内でこれらを管理しようとしましたが、Step Functions に移行することで、リトライポリシーやエラーハンドリングを宣言的に定義でき、Lambda のコードが大幅にシンプルになりました。

### 4. Nova Pro の動画解析能力

Amazon Nova Pro は S3 URI から直接動画を入力でき、フレーム抽出やエンコードの前処理が不要です。チック症状のような微細な身体動作を検出する能力は想定以上に高く、タイムスタンプ付きの観察内容まで出力できます。1 動画あたり約 $0.004 というコストも、プロトタイプからプロダクションへのスケーリングを現実的にしています。

### 5. Amplify Gen 2 + CDK の段階的構築

Amplify Gen 2 は認証やストレージを素早くセットアップでき、CDK カスタムコンストラクトで自由度の高いリソース定義ができます。`backend.ts` での staged activation パターンにより、10 ステップの実装ロードマップに沿って段階的にインフラを有効化でき、短い期間でも確実に動くプロトタイプを段階的に成長させることができました。

### 6. AgentCore Runtime によるエージェントのマネージド実行

Strands Agents SDK で構築した AI エージェントを AgentCore Runtime 上で実行することで、ECS/Fargate のインフラ管理から解放されました。エージェントの Docker イメージを ECR にプッシュするだけでデプロイが完了し、スケーリングやヘルスチェックは AgentCore が自動で処理します。エージェントの開発にビジネスロジックだけに集中できる点が大きな利点でした。

## Future Work

### 1. AgentCore Gateway による MCP Server 化

現在の TicTrack は REST API ベースのアプリケーションですが、次のステップとして Amazon Bedrock AgentCore Gateway を活用し、TicTrack の機能を MCP（Model Context Protocol）Server として公開することを計画しています。これにより、Claude などの AI アシスタントから自然言語で「今週の息子のチック傾向を教えて」「昨日の動画の分析結果を見せて」といった操作が可能になります。既存の API を数行のコードで MCP 互換ツールに変換でき、認証・認可も AgentCore Gateway が一元管理するため、セキュリティを維持したままエージェントからのアクセスを実現できます。

### 2. 医療機関・製薬企業へのデータ提供

TicTrack に蓄積される服薬記録と症状の時系列データは、個人の記録にとどまらない価値を持ちます。匿名化・集約されたデータを医療機関や製薬企業に提供することで、「特定の薬剤がチック症状の頻度や重症度にどう影響するか」といった臨床的知見の蓄積に貢献できます。保護者の同意に基づくオプトイン方式でデータを提供し、チック症状の研究と治療の発展を支援します。

### 3. 専門家連携によるナレッジベースの構築

現在の AI 自動ラベリングは汎用モデルの能力に依存していますが、小児神経科医やチック症の専門家と連携し、専門知識を体系化したナレッジベースを構築することを目指しています。Amazon Bedrock Knowledge Bases と S3 Vectors を活用し、専門家が監修した症状分類基準・観察ガイドライン・ケーススタディを RAG（Retrieval-Augmented Generation）で参照可能にします。これにより、AI ラベリングの精度と信頼性を専門家レベルに近づけ、保護者と医療者の双方にとってより価値の高い情報を提供できるようになります。
